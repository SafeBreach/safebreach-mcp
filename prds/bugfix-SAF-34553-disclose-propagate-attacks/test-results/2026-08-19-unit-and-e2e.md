# Addendum 2 — scope-aware disclosure counts (2026-08-19 17:05)

HEAD: fd8c41f

## A live agent-driven sanity run found a defect 319 green tests had missed

The user connected an agent to the branch's MCP server and worked through the prompt walkthrough
against pentest01. Outcome:

**Confirmed working — including the one thing no test of mine could establish.** The agent relayed
both exclusions unprompted ("45 Propagate (ALM) attacks also match but are excluded... 15 unpublished
drafts hidden") and volunteered, on the total, that 9,656 "is the number a customer sees in the
Playbook UI" — which is the ticket's intent, not text from the tool description. Markers rendered on
all 45 Propagate rows, on ALM attack 13371166, and correctly *not* on Validate attack 1027.

**Defect found.** With `test_type='propagate'` the tool claimed **15 drafts hidden**; the true answer
is **0** — all 15 drafts are Validate, so none were in the Propagate scope. The agent's diagnosis was
exactly right: the count was computed before the scoping.

This is the **same ordering trap T-18 guards for the Propagate count, made in the mirror direction.**
It survived 319 green unit tests because no fixture had drafts confined to the opposite catalog. The
two counts require opposite orders:

| Count | Order | Question it answers |
|---|---|---|
| Propagate | across both catalogs, **before** scoping | "what else matched that this scope hid" |
| Draft | **after** scoping | "what did this scope itself hide" |

Fixed in `fd8c41f`; T-52..T-56 added; split counts now follow `include_drafts` so
`validate_count + propagate_count == total_attacks` always holds.

## Verified live after the fix

Credential Access tactic:

| Scope | Total | Drafts reported hidden |
|---|---|---|
| `validate` | 121 | 15 ✅ |
| `propagate` | 45 | **none** ✅ (was falsely 15) |
| `all` | 166 | 15 ✅ |

Unfiltered:

| Scope | Total | Drafts | Propagate excluded |
|---|---|---|---|
| `validate` | 9,656 | 289 | 111 |
| `propagate` | 111 | none | — |
| `all` | 9,767 | 289 | — |

`166 = 121 + 45` and `9,767 = 9,656 + 111`. Consistent throughout.

## One finding from that run was WRONG, and is recorded so nobody chases it

The agent concluded that `10004035` and `10004039` matched a `T1003` filter while carrying empty MITRE
technique lists, and called it a data-quality bug. They do not: `10004035` carries
`(T1003) OS Credential Dumping` and `(T1212)`; `10004039` carries `(T1003)` alongside four others.
Verified directly against the pentest01 payload. **The filter matched correctly.**

What misled it is a real usability wart: `include_mitre_techniques` defaults to `False`, but technique
filtering auto-enables MITRE extraction internally, so the filter works while the rendered output
omits its own evidence. Pre-existing, not a correctness defect — filed as an 8th finding on SAF-35355.

## pentest01 data quality (console content, not code)

The run also surfaced genuine junk published on pentest01: ids in the 10000000+/20000000+ ranges with
`Modified: None`, names like `Copy of ... 1111` and `new edit -`, one entry (`10000047`) whose
description field is raw Python source, a duplicate NTDS.dit entry (`20007223`), and a `protocol:FTP`
tag on an attack with no FTP involvement. The agent's advice stands: **do not use pentest01 counts for
anything customer-facing.**

`TestPlaybookE2E::test_get_playbook_attack_details_real_api`

```
Failed: E2E test failed: Failed to fetch playbook attacks:
API call failed with status 500: {"error":{"statusCode":500}}
```

Assessed rather than dismissed:

| Question | Answer |
|---|---|
| Does it reproduce? | **No** — passes in isolation, 16.57s |
| Is the test touched by this branch? | **No** — `git diff origin/main..HEAD` on `test_e2e.py` is 217 insertions and zero real deletions (the single apparent deletion is a trailing-newline change, `\ No newline at end of file`) |
| Does this branch change the API call? | No — the fetch path is untouched; only post-fetch filtering and rendering changed |
| Plausible cause | A server-side 500 from the console under e2e load: 37 tests each fetch the full 10,056-move catalog, with `clear_playbook_cache()` in many `setup_method`s, so the suite hammers content-manager's KB endpoint |

**Conclusion: transient, console-side, pre-existing.** Not attributed to this change.

**But it is a real cost worth naming:** this e2e suite refetches a 10k-move catalog dozens of times
against a shared console. It is slow (7 minutes), load-generating, and now demonstrably flaky for
reasons unrelated to any change under test. A future ticket should make the e2e suite share one
catalog fetch per session instead of clearing the cache per test. Left unaddressed here — it is not
SAF-34553's defect and fixing it would expand this change again.
